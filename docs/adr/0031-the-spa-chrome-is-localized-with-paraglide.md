# The SPA chrome is localized with Paraglide; everything else stays English

The frontend chrome — components, label tables, onboarding — is localized into seven
languages (`en`, `ru`, `es`, `de`, `zh-CN`, `pt-BR`, `hi`) with Paraglide JS 2.x. The
UI language is a per-device choice: resolved from localStorage, then the browser's
languages, then English, in one pure module. Server error messages, channel bots, the
CLI, and the HITL popup remain English. The assistant's reply language is not a
setting anywhere — it mirrors the language the user writes in.

## Context

Every user-facing string in the repo was a hardcoded English literal (~1,200–1,400
sites: ~60% SPA, ~250 backend error strings, ~120 channel-bot messages, ~75 CLI
lines). The conversation itself was already language-agnostic — the model mirrors the
user — so the chrome was the only barrier for non-English speakers.

Three structural facts constrained the design. The built SPA is committed to the repo
and CI fails on drift, so localization output must be deterministic. Every API field
is double-declared (Pydantic + zod) under the OpenAPI gate (ADR 0028), so a
server-side language field is a contract change, not a tweak. And backend errors are
plain strings rendered verbatim by the frontend — localizing them means an error-code
registry or per-request locale rendering, an architecture decision of its own.

## Decision

**Paraglide JS 2.x over i18next/svelte-i18n/typesafe-i18n.** Messages compile to
typed functions: a wrong key or missing parameter fails `svelte-check`, which this
repo already runs as a blocking gate twice. Output is deterministic (safe for the
committed bundle), tree-shaken, and adds no runtime dependency. The trade-offs
accepted: all seven locales ship in the one bundle (no lazy loading — switching is
instant and offline-safe), and a locale switch re-renders by re-keying the app tree
rather than per-message reactivity (the documented Paraglide SPA pattern; the
compiled `src/paraglide/` directory is generated by `npm run check`/`build`, never
committed). Rejected: `typesafe-i18n` (documented unresolved gap in Russian
one/few/many plurals; fork-maintenance mode), `svelte-i18n` (stale, untyped keys),
`i18next` (solid runner-up, but weaker build-time guarantees and ~14 kB runtime).

**The UI language is per-device, frontend-only.** It lives in localStorage
(`ag2-lang`) beside theme and accent — not in `config.yaml`, not per Profile, not in
any API schema. Detection never writes the key; only an explicit pick in Settings →
General does, so an unpicked device keeps following its browser. `<html lang>` tracks
the choice.

**Server errors stay English inside a localized UI.** Accepted deliberately for v1
rather than half-solved: doing it properly requires error codes, and doing it
client-side would mean pattern-matching on message strings.

**English is the single source of truth.** The six other catalogs are LLM-generated
from `web/messages/en.json` and committed for review. A parity test (part of
`npm test`, so part of CI) fails when any catalog's key set diverges from English —
translations cannot silently rot. Translations must preserve the deliberate term
distinctions in CONTEXT.md (Directory vs Folder; Attachment vs Upload vs File
reference); the glossary is the term base.

**Right-to-left is out.** All seven launch languages are LTR; nothing in the layout
is mirrored. An RTL language is its own project, not an eighth catalog file.

## Consequences

A new locale is: add the tag in three declared places (message file, inlang project,
`UI_LOCALES`) — the parity test enforces the triangle — and translate one JSON file.
Bundle size grows with each locale since all ship. Every catalog edit requires the
usual SPA rebuild-and-commit or the bundle-freshness job fails. The known anglicisms
that remain (error strings, chat-title "Title Case", English-only onboarding
skip-words, channel/CLI strings) are outside this decision's scope and listed in the
i18n final-sweep notes.
